本章回答“怎样从零设计一个数据库”：从用户需求出发，经概念结构、逻辑结构、物理结构三级抽象，最后实施并长期维护。它是关系模型、SQL、范式理论之后的综合应用章，期末必有一道 10 分左右的 E-R 图转关系模式大题；六阶段流程、数据字典五部分、三类冲突几乎年年以简答、填空形式出现。

7.1数据库设计概述

数据库设计是指对给定应用环境，构造（设计）优化的数据库逻辑模式和物理结构，并据此建立数据库及其应用系统，使之能够有效地存储和管理数据，满足各种用户的应用需求。需求分两类：信息管理要求（存哪些数据对象）与数据操作要求（查询、增、删、改、统计）。目标是提供信息基础设施和高效率运行环境：存取效率高、存储空间利用率高、运行管理效率高。

建设规律是三分技术，七分管理，十二分基础数据；结构（数据）设计与行为（处理）设计要结合。传统软件工程重行为，早期数据库设计重结构，都把二者割裂。

方法上，手工试凑法靠经验、质量难保证、维护代价高；规范设计法强调过程迭代和逐步求精，代表有新奥尔良方法（需求分析、概念设计、逻辑设计、物理设计）、基于 E-R 模型的方法、3NF 方法、面向对象方法与 UML 方法。

  1. 需求分析
  2. 概念结构设计
  3. 逻辑结构设计
  4. 物理结构设计
  5. 数据库实施
  6. 运行维护

六阶段中，需求分析与概念结构设计独立于任何 DBMS，逻辑与物理设计同选用的 DBMS 密切相关；六阶段往往反复。人员：设计人员自始至终参与；DBA 与用户代表参加需求分析和运行维护；开发人员实施阶段参与。

各级模式随阶段形成：需求分析综合各用户需求；概念设计形成独立于机器与 DBMS 的概念模式（E-R 图）；逻辑设计先转数据模型成逻辑模式，再建视图成外模式；物理设计做存储安排、建索引，成内模式。

7.2需求分析

需求分析是设计数据库的起点，结果是否准确直接影响后续各阶段是否合理实用。任务是：调查现实世界要处理的对象，了解原系统概况，明确用户需求，确定新系统功能，并充分考虑今后可能的扩充和改变。调查重点是“数据”和“处理”，要获得三方面要求：信息要求（需要获得信息的内容与性质，由此导出存哪些数据）、处理要求（完成哪些功能、性能要求如何）、安全性与完整性要求。

难点是双方知识不对称：用户缺计算机知识、需求常变；设计人员缺用户专业知识。解法是不断深入与用户交流。调查四步：组织机构、各部门业务活动、明确三类要求、确定系统边界。六种方法：跟班作业、开调查会、请专人介绍、询问、设计调查表请用户填写、查阅记录。分析表达用结构化分析方法（SA）：从最上层组织机构入手，自顶向下、逐层分解。分析报告必须交用户认可。

数据字典是关于数据流图中数据的描述，不是数据本身（与元数据有区别）；需求分析阶段建立，设计过程中不断修改、充实、完善，是详细数据收集和数据分析的主要结果。它由五部分组成：数据项、数据结构、数据流、数据存储、处理过程。数据项是不可再分的最小单位，若干数据项组成数据结构，字典通过定义数据项和数据结构来描述数据流、数据存储的逻辑内容。

7.3.1概念模型与 E-R 模型

把需求抽象为信息结构（概念模型）的过程就是概念结构设计。概念模型真实充分反映现实、易于理解、易于更改、易于向关系/网状/层次模型转换，描述工具是 E-R 图，三要素：实体型用矩形，属性用椭圆形，联系用菱形，均以无向边连接，边上标 1∶1、1∶n 或 m∶n；联系也可以有属性（如选修的“成绩”）。

三类联系：1∶1——A 中每个实体在 B 中至多一个（也可没有），反之亦然，如班级与正班长；1∶n——A 中每个实体在 B 中有 n 个（n≥0），反之 B 中每个实体在 A 中至多一个，如班级与学生；m∶n——A 中每个实体在 B 中有 n 个（n≥0），反之 B 中每个实体在 A 中也有 m 个（m≥0），如课程与学生。两个以上实体型之间也有这三类联系；联系的度＝参与联系的实体型数目。三元例：课程、教师、参考书，一门课可由若干教师讲授、用若干参考书，每个教师只讲一门课、每本参考书只供一门课，故课程与教师、参考书之间是 1∶n。单个实体型内部也可有联系，如职工“领导”职工是 1∶n。

【补充】弱实体：自身属性不足以形成主码、必须依附属主实体才能存在的实体，如“订单细节”依附“订单”。E-R 图中弱实体用双矩形、依赖联系用双菱形；其码＝属主实体的码＋弱实体的部分码，转换时以此组合为主码，属主码作外码。

实体与属性划分两准则：（1）属性不能再具有需要描述的性质，必须是不可分的数据项，不能包含其他属性；（2）属性不能与其他实体具有联系。能当属性就尽量当属性以简化 E-R 图，需要被描述或参与联系则上升为实体。三例：职称不与工资福利挂钩可作属性，否则应作实体；病房号若一个病人只住一个病房可作属性，若病房还要与医生发生“负责”联系则应作实体；仓库号若一种货物只存一个仓库可作属性，若可存多个仓库、仓库有面积属性或与职工有管理联系，则仓库应作实体。【例 7.1】销售管理中，订单细节含零件号、数量，按准则（1）应上升为实体，订单与订单细节是 1∶n；每种产品有不同订货量的折扣，应增设“折扣规则”实体。

易错

①1∶n 方向写反：班级与学生是 1∶n，n 端是学生，“班级号”作外码放进学生表。②漏画联系属性：成绩、供应量必须挂菱形。③两个方向都是“多个”却判成 1∶n——A 对 B 多、B 对 A 也多，就是 m∶n。

口诀：方框装实体，椭圆挂属性，菱形连联系；一一互唯一，一多单向多，多多人人广——判定时先固定一端问“它对面有几个”。

7.3.5概念结构的集成：冲突与冗余

各分 E-R 图面向的问题不同，集成时必有不一致，称为冲突。集成分两步：合并——解决冲突，生成初步 E-R 图；修改和重构——消除不必要冗余，生成基本 E-R 图。

冲突分三类。属性冲突：属性域冲突（类型、范围或集合不同，如零件号一处整数、一处字符型）与单位冲突（公斤/斤/克）。命名冲突：同名异义（不同对象同名）与异名同义（同一对象不同名，如科研项目在财务科叫“项目”、科研处叫“课题”、生产管理处叫“工程”）；可发生在实体、联系或属性一级，靠讨论、协商等行政手段解决。结构冲突：同一对象抽象不同（职工一处是实体、一处是属性），把属性变换为实体或反之；同一实体在各图中属性个数与次序不同，取各子系统属性的并集再调次序；联系类型不同（一处 m∶n、一处 1∶n），按应用语义综合或调整。

类型典型表现解决办法
属性冲突域冲突（类型、范围、集合不同）；单位冲突（公斤/斤/克）统一类型、范围与单位
命名冲突同名异义；异名同义（项目/课题/工程）讨论、协商统一命名
结构冲突同一对象抽象不同；同一实体属性集不同；联系类型不同实体属性互转；属性取并集；按语义调整联系类型

冲突与冗余的结论要能直接背写。

  • 集成两步：合并出初步 E-R 图，重构出基本 E-R 图。

7.4.1E-R 图向关系模型的转换

逻辑结构设计把基本 E-R 图转换为所选 DBMS 支持的数据模型的逻辑结构。E-R 图由实体型、属性、联系组成，关系模型是一组关系模式，所以转换就是把实体型、属性和联系转为关系模式。总原则：一个实体型转为一个关系模式，属性＝实体的属性，码＝实体的码。

（1）1∶1 联系：可独立成表，也可与任意一端合并。独立成表时属性＝两端实体的码＋联系属性，每个实体的码都是候选码（如“管理（BH，XH）”）；合并到某一端时，该端加入另一端的码和联系属性，合并后码不变。

（2）1∶n 联系：可独立成表，也可与 n 端合并。独立成表时属性＝两端码＋联系属性，码是 n 端实体的码（不是组合码）；合并到 n 端时，n 端加入 1 端的码和联系属性，码不变，可减少关系个数，一般更倾向于合并。如部门 dept(dno,dname) 与职工 1∶n：可建 r(dno,cno)，或写成职工(cno,cname,dno)。

（3）m∶n 联系必须独立成表：属性＝各实体的码＋联系属性，码是各实体码的组合，如选修（学号，课程号，成绩）。（4）三个及以上实体的多元联系也独立成表，属性＝各实体码＋联系属性，码是各实体码的组合，如供应（产品号，供应商号，零件号，供应量）。（5）具有相同码的模式可合并：把一个模式的全部属性加入另一个，去掉同义属性（可能同名也可能不同名），调整次序。

联系类型独立成表的属性独立成表的码合并方式
1∶1两端实体的码＋联系属性每个实体的码都是候选码可并入任意一端，加另一端码；码不变

CREATE TABLE SC (
  Sno   CHAR(8)  NOT NULL,
  Cno   CHAR(4)  NOT NULL,
  Grade SMALLINT,
  PRIMARY KEY (Sno, Cno),
  FOREIGN KEY (Sno) REFERENCES Student(Sno),
  FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
-- 1∶n 联系“属于”并入 n 端（学生），加入 1 端（系）的码
ALTER TABLE Student ADD Sdept CHAR(20);
ALTER TABLE Student ADD FOREIGN KEY (Sdept) REFERENCES Dept(Dno);

考点 · 必背

本章分值最高，判分点是“属性取哪些、码是谁”。

  • 实体：一实体一关系，属性＝实体属性，码＝实体码。
  • 1∶1：独立表两端码都是候选码；或并入任一端，码不变。
  • 1∶n：独立表码是 n 端码；或并入 n 端，n 端加 1 端码。
  • m∶n 与多元联系：必须独立成表，码＝各实体码的组合。
  • 相同码的模式可合并，去同义属性、调次序。

例题

【补充例题】“供应商—项目—零件”是 m∶n 的“供应”联系，供应量为联系属性；另有 1∶1 的“仓库—主任”。写出关系模式与码，并给 1∶1 的两种方案。

三元联系独立成表：供应（供应商号，项目号，零件号，供应量），码为（供应商号，项目号，零件号），三个属性同时是参照供应商、项目、零件的外码。1∶1 方案一：负责（仓库号，主任职工号），两属性都是候选码；方案二：并入仓库端 仓库（仓库号，面积，电话，主任职工号）或并入主任端，码均不变。

易错

①1∶n 独立成表时把码写成“两端码的组合”——组合码只属于 m∶n 和多元联系。②1∶1 合并后改变主码——合并只加属性，码不变。③把 m∶n 硬并入一端，产生多值属性、违反 1NF。④合并时忘删同义属性。

口诀：实体先成表，联系看类型；一一合并任意端，一多合并多端算；多多年年建新表，三元码是全组合——1∶1 各码皆候选，1∶n 取 n 端，m∶n 取全组合。

7.4.2数据模型的优化与用户子模式

逻辑设计结果不唯一，得到初步模型后还要调整结构以提高性能，即数据模型的优化，通常以规范化理论为指导。五步：①确定数据依赖；②极小化处理，消除冗余联系；③范式分析，考察部分函数依赖、传递函数依赖、多值依赖，确定属于第几范式；④按处理要求分析，确定是否合并或分解；⑤必要时分解，提高操作效率和存储利用率，分水平分解与垂直分解。

必须记住一个反直觉结论：并不是规范化程度越高的关系就越优。查询经常涉及多个模式的属性时会频繁连接，而连接代价相当高，因此第二范式甚至第一范式也许是适合的；非 BCNF 模式虽有更新异常，但若实际只查询、不更新，就不会产生实际影响。规范化到什么程度，要权衡响应时间和潜在问题两者的利弊。

水平分解把关系的元组分为若干子集合，每个子集合定义一个子关系：对符合 80/20 的，把经常使用的数据（约 20%）分解出来；或使每个事务存取的数据对应一个子关系。垂直分解把 R 的属性分为若干子集合，原则是经常一起使用的属性分解出来；优点是提高某些事务效率，缺点是另一些事务不得不做连接而降低效率，是否采用取决于分解后所有事务的总效率是否提高，且必须保持无损连接性和保持函数依赖。

7.4.3 用户子模式：定义数据库模式主要考虑时间效率、空间效率、易维护；定义外模式（视图）更注重用户习惯与方便，有三方面：①使用更符合用户习惯的别名；②针对不同级别用户定义不同视图以保证安全性——如产品关系上给一般顾客建 产品 1（产品号，产品名，规格，单价），给销售部门建 产品 2（再加车间、生产负责人），成本、合格率等敏感列不出现；③简化用户对系统的使用，把常用复杂查询定义为视图。

易错

①“规范化程度越高越好”是最经典的错误选项。②水平分解分的是行（元组），垂直分解分的是列（属性），别说反。③垂直分解不一定提高效率，要看所有事务总效率。④视图作用是习惯、安全和简化，不是提高物理查询效率。

本节小结

  • 优化五步：定依赖、极小化、判范式、按处理要求权衡、必要时分解。
  • 高范式≠高性能；连接代价高时可降范式，只查不更时非 BCNF 可接受。
  • 水平分解按元组，垂直分解按属性且须无损连接、保持函数依赖。
  • 外模式面向用户：改名、分级授权、封装复杂查询。

7.5数据库的物理结构设计

物理结构是数据库在物理设备上的存储结构与存取方法，依赖选定的 DBMS；为其选取最适合应用要求的结构就是物理设计。两步：①确定物理结构（存取方法和存储结构）；②评价，重点是时间与空间效率。不满足则修改结构，甚至返回逻辑设计。

准备两项：充分了解应用环境、分析要运行的事务以获取参数；充分了解所用 DBMS 的内部特征，特别是存取方法和存储结构。

B+ 树索引三条选择规则：属性经常在查询条件中出现→建（组合）索引；经常作最大值、最小值等聚集函数的参数→建索引；经常在连接条件中出现→建索引。索引过多会增加维护索引和查找索引的开销。HASH 索引适合属性主要出现在等值连接或等值比较选择条件，且满足其一：关系大小可预知且不变；大小动态改变但 DBMS 提供动态 Hash。

聚簇：为提高某属性（组）的查询速度，把该属性（聚簇码）上值相同的元组集中存放于连续物理块。建聚簇索引后，基表数据按聚簇属性值升序或降序存放，索引项顺序与元组物理顺序一致；一个基本表最多只能建一个聚簇索引，适用条件是很少增删、很少修改变长列。

聚簇的主要用途是大大提高按聚簇属性查询的效率——计算机系 500 名学生若分布在 500 个物理块上，至少要 500 次 I/O；同系元组集中后，每读一块可得多个满足条件的元组，显著减少磁盘访问。局限：只能提高某些特定应用的性能；建立与维护开销大，对已有关系建聚簇会使元组物理位置移动、原有索引失效必须重建。适用范围：通过聚簇码访问或连接是主要应用；SQL 中含与聚簇码有关的 ORDER BY、GROUP BY、UNION、DISTINCT 时特别有利。

选择聚簇：候选聚簇有三条——常在一起连接的关系可建组合聚簇；一组属性常在相等比较条件中出现；某属性值重复率很高。再取消：经常全表扫描的、更新远多于连接的、重复出现的（多方案中选总代价最小者）。

存储结构包括关系、索引、聚簇、日志、备份等的存储安排与系统配置，要综合存取时间、存储空间利用率、维护代价，三者常相互矛盾，须权衡折中。存放位置：易变与稳定分开、常用与低频分开；如大表分放两个磁盘以加快存取（多用户下特别有效），日志文件与数据库对象分放不同磁盘。系统配置参数（用户数、缓冲区、物理块大小、装填因子、锁数等）有合理缺省值，物理设计时按环境调整，运行后还要再调。

考点 · 必背

聚簇的定义、唯一性、适用条件是必背三连；B+ 树与 Hash 的分工是选择题常客。

  • 聚簇：聚簇码值相同的元组集中存放在连续物理块；索引项顺序＝元组物理顺序。
  • 一个基本表最多一个聚簇索引；很少增删、很少改变长列才适用。
  • B+ 树管范围与连接；Hash 只管等值；聚簇管“相邻存放”。
  • 存放位置：易变/稳定、常用/低频、日志与数据分开。
  • 评价三指标：存储空间、存取时间、维护代价。

例题

【补充例题】Student 表每块存 20 行，信息系 500 名学生随机分布在各块，查询“信息系全部学生”需多少次 I/O？按系聚簇后约多少次？

随机分布时 500 个元组可能落在 500 个不同块，最坏需 500 次 I/O。按系聚簇后同系元组物理相邻，读一块约得 20 行，约需 500÷20＝25 次 I/O。聚簇把“按聚簇码选择”从随机访问变成块内批量访问，且聚簇码不必逐元组存储，既提速又省空间。

口诀：B+ 树管范围，Hash 管等值，聚簇管相邻——一个表一个聚簇，增删频繁别去碰。

7.6数据库的实施与运行维护

实施三件事：建立数据库结构、组织数据入库、编写与调试应用程序。组织数据入库是实施阶段最主要的工作，方法分人工方法和计算机辅助数据入库；应用程序设计应与数据设计并行，在入库同时调试程序。程序调试完成、少量数据入库后，开始联合调试（试运行），主要工作是功能测试（运行程序、测试各种功能）和性能测试（测量指标、分析是否符合设计目标）。物理设计评价结果粗糙，试运行要实测；不合格需返回物理设计调结构、改参数，有时甚至返回逻辑设计。因入库工作量太大，应采用分期入库：先小批量调试，基本合格后再大批量。试运行阶段系统不稳定、故障随时可能发生，操作人员又不熟悉，必须做好转储和恢复。

运行维护由 DBA 负责，四项：①转储和恢复——制定转储计划，定期备份数据库和日志，故障时尽快恢复；②安全性、完整性控制——初始定义（授予不同操作权限、定义完整性约束）与修改定义（环境变化后修改安全控制、修正约束）；③性能的监督、分析和改进——用监测工具获取性能参数，分析是否处于最佳状态，否则调参改进；④重组织与重构造。

重组织：运行一段时间后记录的不断增删改使物理存储变坏，降低空间利用率和存取效率，故需重组织；分全部重组织和部分重组织（只对频繁增删的表），目标是提高性能；工作是重排存储位置、回收垃圾、减少指针链。重组织不改变原设计的数据逻辑结构和物理结构。重构造：应用环境变化使原设计不能满足新需求，需调整数据库的模式和内模式——增删数据项、改变数据项类型、增删表、改变容量、增删索引。重构造程度有限：变化太大或代价太大，说明系统生命周期结束，应重新设计。

对比项重组织重构造
动因增删改使物理存储变坏，效率下降应用环境变化，原设计不能满足新需求
改变什么只重排物理存储：移位置、回收垃圾、减少指针链调整模式与内模式：增删数据项/表/索引，改类型、改容量
是否改结构不改变逻辑结构和物理结构改变逻辑模式与内模式
程度可全部或部分进行程度有限，变化过大则重新设计新系统

易错

①把重组织说成“重新设计表结构”——它不改逻辑结构和物理结构。②试运行只做功能测试——还要做性能测试并实测指标。③试运行不合格只能改物理结构——也可能返回逻辑设计。④数据入库是实施阶段最主要的工作，不是次要工作。

7.7小结：全章串讲与答题模板

全章一条线：需求分析出数据字典（现实世界需求）→概念设计出 E-R 图（信息世界模型）→逻辑设计出逻辑模式与外模式→物理设计出内模式→实施→运行维护（转储、安全、性能、重组重构），过程中常有反复。

设计大题固定套路：①圈实体与联系，判 1∶1、1∶n、m∶n（三元单独标）；②画 E-R 图（矩形实体、椭圆属性、菱形联系，边标基数）；③按“实体先成表、联系看类型”转换，1∶1 并任一端、1∶n 并 n 端、m∶n 与多元独立成表；④标主码（下划线）与外码，说明参照；⑤问优化则答规范化检查、水平/垂直分解、视图；⑥问物理答索引/聚簇与评价指标。

本节小结

  • 六阶段可反复；需求分析与概念设计独立于 DBMS，逻辑与物理设计依赖 DBMS。
  • 模式形成：概念模式（E-R 图）→ 逻辑模式＋外模式 → 内模式。
  • 转换一句话：实体成表，1∶1 任并、1∶n 并 n 端、m∶n 与多元必独立、同码可合并。
  • 优化权衡范式与性能；物理抓存取方法、存储位置与评价；维护抓四项日常工作。
