并发控制

已掌握 0 / 9 节

并发控制要回答一个问题：多个事务同时读写同一批数据时，系统凭什么保证结果与"一个一个排队执行"一样正确。它是事务篇的收尾，把第 10 章的 ACID 落到"调度"这一层，也是全书唯一系统讲"锁"的地方。期末卷上，三级封锁协议、两段锁协议、意向锁几乎年年出简答，给一个调度画优先图判冲突可串行化是稳定的 8 分计算题，锁相容矩阵与死锁判定则常以选择、填空出现。

11.1并发控制概述

多用户数据库系统指允许多个用户同时使用的数据库系统，典型如飞机订票系统、银行数据库系统，其特点是同一时刻并发运行的事务数可达数百上千个。并发控制的基本单位是事务，机制的任务只有三句话：对并发操作进行正确调度、保证事务的隔离性、保证数据库的一致性。

多事务的执行方式有三种。串行执行：每个时刻只有一个事务运行，其它事务必须等它结束才能运行；n 个事务组共有 n! 个调度策略，且不能充分利用系统资源、发挥数据库共享资源的特点。交叉并发（Interleaved Concurrency）：单处理机系统中并行事务的并行操作轮流交叉运行，物理上并没有真正并行，但能减少处理机的空闲时间、提高系统效率。同时并发（Simultaneous Concurrency）：多处理机系统中每个处理机运行一个事务，实现真正的并行运行；不过从逻辑调度角度看，其效果仍可建模为某种交叉调度，因为共享资源的访问仍需同步。

课件用转账例子说明"串行一定对、但顺序不同结果不同"：A 有 1000 元、B 有 2000 元，T1 是 A 转 50 元给 B，T2 是 A 转 10% 给 B。按 T1→T2 执行得 A=855、B=2145；按 T2→T1 执行得 A=850、B=2150。两个结果的 A+B 都等于 3000，都是正确结果，数值却不同。这说明"正确"的标准不是结果唯一，而是结果等于某一次串行执行的结果，这正是 11.5 可串行化定义的由来。

并发执行会产生多个事务同时存取同一数据的情况，可能存取和存储不正确的数据，破坏事务的隔离性和数据库的一致性。课件归纳了三种数据不一致性，记号约定为 R(x) 读数据 x、W(x) 写数据 x。

1. 丢失修改（Lost Update）：两个事务 T1 和 T2 读入同一数据并修改，T2 的提交结果破坏了 T1 提交的结果，导致 T1 的修改被丢失。【例11.1】飞机订票系统中甲、乙两个售票点对应 T1、T2：① T1 读出某航班机票余额 A=16；② T2 读出同一余额 A=16；③ T1 卖出一张，A←A−1 得 15 写回；④ T2 也卖出一张，仍按自己读到的 16 计算，A←A−1 得 15 写回。明明卖出两张票，余额只减少 1，原因是第④步 T2 的写回覆盖了 T1 的修改。

2. 不可重复读（Non-repeatable Read）：事务 T1 读取数据后，事务 T2 执行更新操作，使 T1 无法再现前一次读取结果。它包含三种情况：（1）T2 修改——T1 读 A=50、B=100 求和 150，T2 读同一 B 后令 B←B*2 写回 200，T1 为校对重读 B 得 200，求和 250 与第一次不一致；（2）T2 删除——T1 按条件读出若干记录后，T2 删除了其中部分记录，T1 再按相同条件读时发现记录"神秘消失"；（3）T2 插入——T1 按条件读出记录后 T2 插入新记录，T1 再读时发现多出记录。后两种情况课件称为幻影现象（Phantom Row）。

3. 读"脏"数据（Dirty Read）：事务 T1 修改某一数据并写回磁盘，T2 读取同一数据后，T1 因某种原因被撤销，已修改的数据恢复原值，T2 读到的数据就与数据库中的数据不一致，这个值即"脏"数据。例：T1 读 C=100，C←C*2 写回 200；T2 读到 C=200；T1 回滚使 C 恢复 100，T2 手里的 200 就是作废值。

三种不一致的根源是并发操作破坏了事务的隔离性。并发控制就是用正确的方式调度并发操作，使一个用户事务的执行不受其它事务干扰，从而避免数据不一致。但也要注意：并非所有应用都要求绝对一致，例如数据量很大的统计工作读到一些"脏"数据对统计精度没什么影响，可以降低一致性要求以减少系统开销。并发控制的主要技术有封锁、时间戳、乐观控制法、多版本并发控制（MVCC），本章讲其中最主流的一种——封锁。

考点 · 必背

三种不一致性的定义、典型操作序列、由哪一级封锁协议解决，是本课程最稳定的送分点，简答、选择、填空都可能出。

  • 丢失修改：两个事务都读、都写同一数据，后写的覆盖先写的（例11.1 机票余额 16→15）。
  • 不可重复读：T1 先读，T2 后写/删/插，T1 再读值变了；删、插两种合称幻影现象。
  • 读"脏"数据：T1 写、T2 读，之后 T1 回滚，T2 读到的是作废值。
  • 三者都源于并发破坏隔离性；主要技术为封锁、时间戳、乐观控制法、MVCC。

易错

"丢失修改"与"不可重复读"最容易混，判据只有一条：看 T1 有没有写。丢失修改是 T1、T2 都写了同一数据，损失的是 T1 的修改；不可重复读是 T1 只读、T2 写，损失的是 T1 前后两次读的一致性。另外两个常见误判：一是把幻影现象当成独立的第四类不一致，它只是不可重复读的第（2）（3）种情形；二是把"读脏数据"解释成"读到过期数据"，其要害是读到将被回滚的未提交值，不是旧值。

例题

补充例题：判断下列并发执行序列各属于哪种数据不一致性，并说明理由。(1) T1：R(A)=100，A←A+10，W(A)=110；T2：R(A)=100，A←A−10，W(A)=90。(2) T1：R(B)=50；T2：R(B)=50，B←0，W(B)=0；T1：R(B)=0。(3) T1：R(C)=30，C←C+5，W(C)=35；T2：R(C)=35；T1：ROLLBACK。

(1) 丢失修改。两个事务读入同一数据后各自修改，T2 最后写回 90，把 T1 的 +10 覆盖掉了。(2) 不可重复读（修改型）。T1 前后两次读 B 之间 T2 改写了 B，T1 得到 50 和 0 两个不同值。(3) 读"脏"数据。T2 读到的 35 是 T1 尚未提交的修改值，T1 回滚后 C 恢复 30，T2 读到的是作废数据。
判别线索：两写→丢失修改；先读后写→不可重复读；写了又回滚→脏读。

口诀：两写丢失、一读一写重复不了、回滚留脏——前半句管丢失修改（双方都写），中句管不可重复读（T1 只读、T2 写），后半句管脏读（写方回滚）。答题时先数"谁写了"，再判类型。

本节小结

  • 并发控制以事务为单位，任务是对并发操作正确调度、保证隔离性与一致性。
  • 三种执行方式：串行（n! 个调度、资源利用率低）、交叉并发（单机轮流交叉）、同时并发（多机真并行）。
  • 三类不一致：丢失修改、不可重复读（含幻影现象）、读脏数据；并发控制的主要技术有封锁、时间戳、乐观控制法、MVCC。

11.2封锁

封锁就是事务 T 在对某个数据对象（例如表、记录等）操作之前，先向系统发出请求，对其加锁。加锁后事务 T 对该数据对象有了一定的控制，在 T 释放它的锁之前，其它事务不能更新此数据对象。封锁是实现并发控制的一个非常重要的技术。

一个事务对某个数据对象加锁后究竟拥有什么样的控制，由封锁类型决定。基本封锁类型只有两种：排它锁（Exclusive Locks，X 锁，又称写锁）和共享锁（Shared Locks，S 锁，又称读锁）。

X 锁：若事务 T 对数据对象 A 加上 X 锁，则只允许 T 读取和修改 A，其它任何事务都不能再对 A 加任何类型的锁，直到 T 释放 A 上的锁。它保证其它事务在 T 释放 A 上的锁之前不能再读取和修改 A。

S 锁：若事务 T 对数据对象 A 加上 S 锁，则 T 可以读 A 但不能修改 A，其它事务只能再对 A 加 S 锁，而不能加 X 锁，直到 T 释放 A 上的 S 锁。它保证其它事务可以读 A，但在 T 释放 S 锁之前不能对 A 做任何修改。

考点 · 必背

锁相容矩阵年年以选择或填空出现，判断依据只有类型，不看数据内容、不看事务大小。

  • X 锁 = 写锁：持锁事务可读可写；其它事务连读都不行。
  • S 锁 = 读锁：持锁事务只能读、不能写；其它事务只能加 S 锁。
  • X–X、X–S 不相容；S–S 相容；任一方无锁则相容。
  • 判断"某请求能否批准"：查矩阵得 Y 就立即批准，得 N 就进入等待队列。

易错

三个高频错误：① 以为"S 锁下持锁事务也能改数据"——S 锁只给读权限，要改必须先把 S 锁升级为 X 锁；② 以为"X 锁只挡别人的写"——X 锁连别人的读也挡，否则防不住脏读；③ 把相容矩阵读成"行是已持有、列是请求"，方向一反，结论就全错。补充一个课件未展开的点：锁升级（S→X）在多个事务同时持有 S 锁时会互相等待，可能引发死锁，因此不少系统干脆一次性申请 X 锁。

例题

补充例题：数据对象 A 上，T1 已持有 S 锁。问下列请求能否立即批准：(1) T2 请求 S 锁；(2) T2 请求 X 锁；(3) T1 请求把 S 锁升级为 X 锁，此时 T2 也持有 A 上的 S 锁。

(1) 能。查表 2，S 列 S 行得 Y，多个事务可同时持 S 锁共享读。(2) 不能，需等待。S 列 X 行得 N，只要有人持 S 锁，任何人（包括已持 S 锁者之外的）都不能加 X 锁。(3) 不能，T1 也需等待。升级等价于请求 X 锁，T2 的 S 锁未释放就不相容；若 T1、T2 都持 S 锁又都申请升级，双方互等，构成死锁。
结论：S 锁可共享、X 锁独占；锁升级是被相容矩阵约束的普通请求，不是特权操作。

口诀：X 独占、S 共享；X 六亲不认，S 只认自家人——X 锁与 X、S 都不相容，S 锁只与 S 相容。答题先写"谁持有什么锁"，再查矩阵，一步都别跳。

11.3封锁协议

在运用 X 锁和 S 锁对数据对象加锁时，需要约定一些规则，这些规则称为封锁协议（Locking Protocol）。要约定的其实只有三件事：何时申请 X 锁或 S 锁、持锁时间多长、何时释放。对封锁方式规定不同的规则，就形成不同的封锁协议，它们分别在不同程度上为并发操作的正确调度提供保证。

一级封锁协议：事务 T 在修改数据 R 之前必须先对其加 X 锁，直到事务结束才释放（正常结束 COMMIT、非正常结束 ROLLBACK 都算结束）。作用：可防止丢失修改，并保证事务 T 是可恢复的。注意它只约束写：仅仅是读数据而不修改是不需要加锁的，所以它不能保证可重复读，也不能保证不读"脏"数据。

回到例11.1 的售票序列：T1 读 A 之前先 Xlock A，T2 再请求 Xlock A 被拒绝，只能一直等待；T1 修改、写回、COMMIT 并 Unlock A 之后，T2 才获得 A 上的 X 锁，此时读到的 A 已是 15，再减 1 得 14 写回。两张票对应余额减 2，丢失修改被避免。这里的关键不是"加了锁"，而是X 锁一直持有到事务结束，使 T2 无法在 T1 提交前读到中间值。

二级封锁协议：在一级封锁协议的基础上，加上事务 T 在读取数据 R 之前必须先对其加 S 锁，读完后即可释放 S 锁。作用：可防止丢失修改和读"脏"数据。由于读完数据后立即释放 S 锁，它不能保证可重复读。

它防脏读的过程是：T1 对 C 加 X 锁并把值改成 200 写回；T2 请求在 C 上加 S 锁，因 T1 已加 X 锁只能等待；T1 因故被撤销，C 恢复原值 100 并释放 X 锁；T2 这才获得 S 锁读到 100。T2 读到的始终是已提交的值，脏数据被挡住。

三级封锁协议：在一级封锁协议的基础上，加上事务 T 在读取数据 R 之前必须先对其加 S 锁，直到事务结束才释放。作用：可防止丢失修改、读脏数据和不可重复读，三类不一致全部解决。

它防不可重复读的过程是：T1 在读 A、B 之前先对二者加 S 锁，其它事务只能再加 S 锁而不能加 X 锁，即只能读不能改；T2 为修改 B 申请 X 锁被拒绝，只能等 T1 释放；T1 为验算重读 A、B，读出的 B 仍是 100，求和仍是 150；T1 结束才释放 A、B 上的 S 锁，T2 这时才获得 B 的 X 锁。

三级协议的主要区别只有一条：什么操作需要申请封锁，以及何时释放锁（持锁时间）。不同的封锁协议使事务达到的一致性级别不同：封锁协议级别越高，一致性程度越高，但并发度越低。实际系统不一律用三级，原因就在这里——读多写少的应用用三级会把大量读操作互相阻塞到事务结束。

考点 · 必背

本节的考法是"给一张表填三个 √"或"某协议解决了什么、没解决什么"，必须逐字记住加锁与释放时机。

  • 一级：写前加 X 锁，持到事务结束；防丢失修改，保证事务可恢复；读不加锁，故不防脏读、不防不可重复读。
  • 二级：一级 + 读前加 S 锁，读完即放；防丢失修改 + 防脏读；不防不可重复读。
  • 三级：一级 + 读前加 S 锁，持到事务结束；三类不一致全防。
  • 级别越高一致性越强、并发度越低；三级的 X 锁与 S 锁都在事务结束时才释放。

易错

三个必踩的坑：① 认为"一级协议给写加了 X 锁，所以也能防脏读"——写方的 X 锁只挡别人写，读方不加 S 锁照样能读到未提交值，一级防不住脏读；② 把二级的"S 锁读完即放"记成"事务结束才放"，那样二级就等于三级了，二者的唯一差别就在这里；③ 答"三级协议能防幻影现象"要谨慎：课件把插入、删除归入不可重复读，三级协议通过锁住已读记录防住修改型，但对新插入的记录需要范围锁/谓词锁才能真正防幻影（补充知识），答题写"三级可防不可重复读（含课件所归的幻影情形）"最稳。

例题

补充例题：某教务系统三个场景，分别指出最低需用哪一级封锁协议，并说明理由。(1) 统计课程平均分，只读不写，要求同一事务内两次统计结果一致；(2) 学生选课，读余量后把余量减 1 写回，不允许出现超额录取；(3) 财务对账，读取某账户余额后可能回滚，绝不允许读到其它事务未提交的中间值，但不要求同一事务两次读一致。

(1) 三级。要求同一事务内两次读结果一致，即保证可重复读；只有三级的 S 锁持到事务结束才能做到。(2) 一级。核心是防止丢失修改（读—改—写回），修改前加 X 锁并持到事务结束即可；若还想防脏读可提到二级。(3) 二级。要求不读脏数据，二级的"读前加 S 锁"已足够；因为不要求可重复读，不必用三级，用三级反而降低并发度。
判题套路：先写出该场景怕哪种不一致，再反查表 3，不要凭"越高越好"直接写三级。

口诀：一级写到底、二级读锁读完放、三级两锁都到底——"到底"指持到事务结束。记不住时反推：S 锁放得越晚，越能防不可重复读；X 锁放得越晚，越能防丢失修改。

本节小结

  • 封锁协议 = 何时加锁 + 持锁多久 + 何时释放；三级协议的区别只在 S 锁的释放时机与是否加 S 锁。
  • 一级防丢失修改，二级再防脏读，三级再防不可重复读；级别越高一致性越强、并发度越低。
  • X 锁在三级协议中一律持到事务结束，这是"可恢复"的前提。

11.4活锁和死锁

封锁技术可以有效地解决并行操作的一致性问题，但也带来两个新问题：死锁与活锁。二者都不是数据错误，而是事务调度层面的"等不到"，考试常让考生区分二者的成因与对策。

活锁的情形：事务 T1 封锁了数据 R，T2 请求封锁 R 于是等待；T3 也请求封锁 R，当 T1 释放 R 上的封锁之后，系统首先批准了 T3 的请求，T2 仍然等待；T4 又请求封锁 R，当 T3 释放后又批准了 T4……T2 有可能永远等待。这就是活锁——事务并非被对方锁住，而是被后来者反复插队，永远轮不到它。

避免活锁的办法是采用先来先服务（FCFS）策略：当多个事务请求封锁同一数据对象时，按请求封锁的先后次序对这些事务排队；该数据对象上的锁一旦释放，首先批准申请队列中第一个事务获得锁。这条策略只改变批准顺序，不改变锁的类型与相容性判断。

死锁的情形：事务 T1 封锁了数据 R1，T2 封锁了数据 R2；T1 又请求封锁 R2，因 T2 已封锁 R2 于是 T1 等待 T2 释放；接着 T2 又申请封锁 R1，因 T1 已封锁 R1，T2 也只能等待 T1 释放。T1 在等 T2、T2 在等 T1，两个事务永远不能结束。产生死锁的原因是两个或多个事务都已封锁了一些数据对象，然后又都请求对已为其它事务封锁的数据对象加锁，从而出现死等待。预防死锁就是要破坏这个条件。

预防方法之一：一次封锁法。要求每个事务必须一次将所有要使用的数据全部加锁，否则就不能继续执行。它有两个问题：降低系统并发度；难于事先精确确定封锁对象——数据库中数据是不断变化的，原来不要求封锁的数据在执行过程中可能变成封锁对象，很难事先精确确定每个事务要封锁的数据对象。若把"可能要用"的对象全部加锁，并发度会进一步降低。

预防方法之二：顺序封锁法。预先对数据对象规定一个封锁顺序，所有事务都按这个顺序实行封锁。它的问题：维护成本高——数据库系统中封锁的数据对象极多，并且随数据的插入、删除不断变化，维护这样的封锁顺序非常困难、成本很高；难以实现——事务的封锁请求可以随着事务的执行动态决定，很难事先确定每个事务要封锁哪些对象，也就很难按规定顺序施加封锁。

结论：在操作系统中广为采用的预防死锁策略并不太适合数据库的特点，数据库管理系统在解决死锁问题上更普遍采用的是诊断并解除死锁的方法。

诊断方法之一：超时法。如果一个事务的等待时间超过了规定的时限，就认为发生了死锁。优点是实现简单；缺点是有可能误判死锁（把等待时间长的正常事务当成死锁而撤销），且时限若设置得太长，死锁发生后不能及时发现。

诊断方法之二：等待图法。用事务等待图动态反映所有事务的等待情况。事务等待图是一个有向图 G=(T，U)：T 为结点集合，每个结点表示正运行的事务；U 为边的集合，每条边表示事务等待的情况，若 T1 等待 T2，则画一条从 T1 指向 T2 的有向边。并发控制子系统周期性地（比如每隔数秒）生成事务等待图并检测，如果发现图中存在回路，就表示系统中出现了死锁。图中可能在大回路里还套着小回路（如 T3 同时等待 T2）。

解除死锁：选择一个处理死锁代价最小的事务将其撤销，释放此事务持有的所有的锁，使其它事务能继续运行下去。注意撤销的判据是"代价最小"，不是"来得最晚"或"锁得最多"。

例题

补充例题：某时刻事务等待关系为 T1 等 T2、T2 等 T3、T3 等 T1，同时 T4 等 T2。(1) 画出等待图并判断是否有死锁，涉及哪些事务；(2) 若系统要用"撤销代价最小"的原则解除死锁，而各事务已修改的元组数为 T1=5、T2=40、T3=2，应撤销谁？

(1) 结点 T1、T2、T3、T4，边 T1→T2、T2→T3、T3→T1、T4→T2。存在回路 T1→T2→T3→T1，故有死锁，死锁涉及 T1、T2、T3；T4 只等待、不在回路上，它是被牵连的等待者，撤销回路中任一事务后 T4 即可继续。
(2) 回路中代价最小的是 T3（只改了 2 个元组），撤销 T3 并释放其锁，T2 得以继续，回路被打断，T4 也随之解开。
要点：只判回路内的结点为死锁事务；撤销范围也只限回路内的"代价最小者"。

口诀：活锁靠排队，死锁靠等图——活锁用先来先服务，死锁用等待图找回路；预防用一次封锁／顺序封锁，解除撤销代价最小者。

11.5并发调度的可串行性

数据库管理系统对并发事务不同的调度可能会产生不同的结果。串行调度是正确的；执行结果等价于串行调度的调度也是正确的，称为可串行化调度。这一节给出"正确调度"的判据，是全章理论味最重、也最容易出计算题的地方。

可串行化（Serializable）调度的定义：多个事务的并发执行是正确的，当且仅当其结果与按某一次序串行地执行这些事务时的结果相同。可串行性（Serializability）是并发事务正确调度的准则：一个给定的并发调度，当且仅当它是可串行化的，才认为是正确调度。

【例11.2】两个事务：T1 为"读 B；A=B+1；写回 A"，T2 为"读 A；B=A+1；写回 B"，设 A、B 初值均为 2。串行 T1→T2：T1 读 B=2，A=3 写回；T2 读 A=3，B=4 写回，结果 A=3、B=4。串行 T2→T1：T2 读 A=2，B=3 写回；T1 读 B=3，A=4 写回，结果 B=3、A=4。若并发执行中两事务都先读后写，各自读到的都是初值 2，则算出 A=3、B=3——与两个串行结果都不同，是不可串行化的错误调度。若把 T2 的"读 A"推迟到 T1 写回 A 之后，结果与串行 (a) 相同，就是可串行化的调度。

直接按定义判可串行化，要把所有串行结果都算出来比较，代价太高。课件给出一个更严格、可机械判定的条件：冲突可串行化，商用系统中的调度器采用的就是它。

冲突操作是指不同的事务对同一数据的读写操作和写写操作：Ri(x) 与 Wj(x)（事务 Ti 读 x、Tj 写 x，i≠j），以及 Wi(x) 与 Wj(x)。其它操作都是不冲突操作、可以交换顺序：(Ri(x), Rj(y))、(Ri(x), Wj(y))、(Wi(x), Rj(y))、(Wi(x), Wj(y))（x≠y，即读写的是不同数据）。

由此得到不能交换（Swap）的动作只有两类：同一事务的两个操作；不同事务的冲突操作。这条结论是画优先图的全部依据——只有冲突才产生先后约束。

冲突可串行化的定义：一个调度 Sc 在保证冲突操作的次序不变的情况下，通过交换两个事务不冲突操作的次序得到另一个调度 Sc′，如果 Sc′ 是串行的，称调度 Sc 是冲突可串行化的调度。若一个调度是冲突可串行化的，则一定是可串行化的调度，反之不然。

判定用优先图（前趋图），步骤固定：

  1. 以每个事务为一个结点，标出调度中出现的全部事务。
  2. 扫描调度序列，找出每一对冲突操作；若 Ti 的冲突操作出现在 Tj 之前，画一条有向边 Ti→Tj。
  3. 图无回路，则调度冲突可串行化；有回路，则不是冲突可串行化的调度。
  4. 无回路时做拓扑排序，得到的顺序就是与该调度等价的串行执行顺序（等价串行调度可能不唯一）。

【例11.3】Sc1 = r1(A) w1(A) r2(A) w2(A) r1(B) w1(B) r2(B) w2(B)。冲突对有三组：w1(A) 与 r2(A)、w1(A) 与 w2(A)、w1(B) 与 r2(B)、w1(B) 与 w2(B)，全部是 T1 的操作在前，于是只有边 T1→T2，无回路。Sc1 等价于串行调度 T1,T2，是冲突可串行化的调度（其串行序列 Sc2 = r1(A)w1(A)r1(B)w1(B)r2(A)w2(A)r2(B)w2(B) 就是把 T1 的动作整体前移得到）。

该图对应的调度是 补充例题：S = r1(A) w1(A) r2(A) w2(B) r3(B) w3(A)。逐个找冲突：w1(A) 在 r2(A) 之前 → T1→T2；w2(B) 在 r3(B) 之前 → T2→T3；w1(A) 在 w3(A) 之前 → T1→T3。图中无回路，冲突可串行化，等价串行序为 T1→T2→T3。注意 T3 读的是 B、写的是 A，与 T2 只在 B 上冲突，不要漏掉 w1(A) 与 w3(A) 这一对跨事务写写冲突。

冲突可串行化是可串行化的充分条件，不是必要条件。【例11.4】T1=W1(Y)W1(X)，T2=W2(Y)W2(X)，T3=W3(X)。调度 L1=W1(Y)W1(X) W2(Y)W2(X) W3(X) 是串行调度。调度 L2=W1(Y)W2(Y)W2(X)W1(X)W3(X) 不满足冲突可串行化：W1(Y) 与 W2(Y) 冲突要求 T1 在 T2 前，W2(X) 与 W1(X) 冲突要求 T2 在 T1 前，两条边构成回路。但 L2 却是可串行化的——执行结果 Y 的值等于 T2 写的值、X 的值等于 T3 写的值，与串行调度 L1 的结果完全相同。原因是这些写操作写的是"盲写"，谁最后写谁生效，冲突次序被覆盖掉了。

本节是全章唯一的固定计算题：给调度画优先图、判冲突可串行化、写等价串行序。

  • 冲突可串行化是充分不必要条件（例11.4 的 L2 可串行化但非冲突可串行化）。

① 把"读读"也算冲突：R1(A) 与 R2(A) 不冲突，不画边，多画一条边就可能凭空造出回路。② 把同事务的两个操作也去交换：同一事务的操作次序不可换，否则调度本身就变了。③ 只找读写冲突、漏掉写写冲突——例11.4 与图 11-1 里的 T1→T3 都是写写冲突。④ 认为"有回路就一定不可串行化"：回路只否定冲突可串行化，是否真的可串行化还要看结果（如 L2）。⑤ 拓扑序写错方向：边是"先执行者→后执行者"，等价串行序必须与边同向。

补充例题：已知调度 S = r1(A) w2(A) r2(B) w3(B) r3(C) w1(C)，A、B、C 初值任意。(1) 画优先图并判断 S 是否冲突可串行化；(2) 若不是，说明它为什么可能仍然是可串行化的。

(2) 回路说明任何串行顺序都会颠倒某一对冲突操作的次序，S 的结果一般与所有串行结果都不同，通常也确实不可串行化；但"有回路"只是否定冲突可串行化，若这些冲突写出的值恰好被后续写覆盖（如例11.4 的盲写），仍可能结果等价于某串行调度，此时它可串行化却不是冲突可串行化。

11.6两段锁协议

数据库管理系统普遍采用两段锁协议（2PL）的方法实现并发调度的可串行性，从而保证调度的正确性。协议内容只有两条：在对任何数据进行读、写操作之前，事务首先要获得对该数据的封锁；在释放一个封锁之后，事务不再申请和获得任何其它封锁。

"两段"的含义是把事务分成两个阶段。第一阶段是获得封锁，也称扩展阶段：事务可以申请获得任何数据项上的任何类型的锁，但是不能释放任何锁。第二阶段是释放封锁，也称收缩阶段：事务可以释放任何数据项上的任何类型的锁，但是不能再申请任何锁。

Slock A    Unlock A    Slock B    Xlock C    Unlock C    Unlock B

2PL 与可串行化的关系（本章第一必考简答）：若并发事务都遵守两段锁协议，则对这些事务的任何并发调度策略都是可串行化的。更准确地说，与 2PL 事务的调度 S 冲突等价的串行调度，是事务顺序与其第一个解锁顺序相同的那个串行调度。课件给出归纳法证明的思路：设 Ti 是 S 中第一个有解锁动作的事务，则 Ti 的任一动作前不可能存在来自其它事务的冲突动作（否则由 Ui(x) 早于 Uj(y)、而 Wi(y) 前有 Wj(y)，会违反两段锁协议），于是 Ti 的全部动作可以非冲突地整体前移到调度开始；对剩余 n−1 个事务归纳即得。

反过来不成立：事务遵守两段锁协议是可串行化调度的充分条件，而不是必要条件。若并发事务的一个调度是可串行化的，不一定所有事务都符合两段锁协议。课件用三张调度图说明：(a) 遵守 2PL，可串行；(b) 不遵守 2PL（读完 B 立即 Unlock B，之后又对 A 加锁），但该调度恰好可串行；(c) 不遵守 2PL（两事务都先读后写），不可串行。可见"不遵守 2PL"既可能可串行也可能不可串行，2PL 只是保证可串行的一个充分手段。

2PL 与一次封锁法的关系（易被忽略的考点）：一次封锁法要求每个事务必须一次将所有要使用的数据全部加锁，否则不能继续执行，因此一次封锁法遵守两段锁协议；但是两段锁协议并不要求事务必须一次将所有要使用的数据全部加锁，因此遵守两段锁协议的事务可能发生死锁。课件的死锁例：T1 先 Slock B、Slock A，随后请求 Xlock A；T2 先 Slock A，随后请求 Xlock B——双方各持一把 S 锁又都等对方的 X 锁，形成死锁（S 锁与 S 锁相容，所以两把 S 锁能同时加上，这正是 2PL 挡不住死锁的原因）。

补充：若进一步要求事务的所有锁都持到事务结束（COMMIT 或 ROLLBACK）才释放，称为严格两段锁协议（Strict 2PL），它除可串行性外还能避免级联回滚；只要求排它锁持到事务结束的称为强两段锁协议。工业系统普遍实现的是严格 2PL 的变体。两段锁协议解决的是"正确性"，死锁要靠 11.4 的诊断与解除来兜底。

考点 · 必背

2PL 的两条规则、两个阶段、与可串行化的充分关系、不能避免死锁，四点必须能一口气写完。

  • 规则：读写下前先加锁；解锁之后不再加锁。
  • 扩展阶段：只申请、不释放；收缩阶段：只释放、不申请；分界点是第一个 Unlock。
  • 全部事务遵守 2PL ⇒ 任何并发调度都可串行化；等价串行序 = 第一个解锁的顺序。
  • 2PL 是充分不必要条件；一次封锁法遵守 2PL，但 2PL 不要求一次加全锁，故 2PL 不能避免死锁。

易错

① 把 2PL 说成"两阶段提交（2PC）"，二者毫无关系：2PL 是加锁规则，2PC 是分布式事务的提交协议。② 认为"2PL 保证不死锁"——它只保证可串行化，死锁是另一回事。③ 认为"遵守 2PL 的事务必须在事务结束时才解锁"——那是严格 2PL，普通 2PL 允许在收缩阶段提前解锁，只是解锁后不能再加锁。④ 判断某序列是否遵守 2PL 时只看"加锁是否成段"，漏看"解锁后是否又申请"——后半条才是最容易违反的。

例题

补充例题：判断下列封锁序列是否遵守两段锁协议，并说明理由；对遵守者指出收缩阶段从哪一步开始。(1) Slock A，Slock B，Unlock A，Xlock C，Unlock B，Unlock C；(2) Xlock A，Xlock B，Unlock A，Unlock B；(3) Slock A，Unlock A，Slock B，Unlock B。

(1) 不遵守。Unlock A 之后又申请了 Xlock C，违反"释放一个封锁后不再申请任何封锁"。(2) 遵守。两个加锁在前、两个解锁在后，扩展阶段为 Xlock A、Xlock B，收缩阶段从 Unlock A 开始。(3) 不遵守。Unlock A 之后又申请 Slock B。
判题口诀：找到第一个 Unlock，它前面不许有 Unlock，它后面不许有 Lock。另外注意：遵守 2PL 只说明该事务参与的任何调度都可串行化，并不说明它不会死锁。

口诀：扩展只加不放，收缩只放不加，分界在第一把解锁——再补一句"2PL 保可串行、不保不死锁"，简答就能拿满。

本节小结

  • 2PL 把事务的封锁分为扩展阶段（只加锁）与收缩阶段（只解锁），第一个 Unlock 是分界点。
  • 全部事务遵守 2PL ⇒ 调度可串行化；等价串行序与各事务第一个解锁的先后一致。
  • 2PL 是可串行化的充分不必要条件；一次封锁法遵守 2PL，而 2PL 事务仍可能死锁。

11.7封锁的粒度与多粒度封锁

封锁对象的大小称为封锁粒度（Granularity）。封锁的对象可以是逻辑单元，也可以是物理单元：在关系数据库中，逻辑单元有属性值、属性值的集合、元组、关系、索引项、整个索引、整个数据库等；物理单元有页（数据页或索引页）、物理记录等。

封锁粒度与系统的并发度和并发控制的开销密切相关：封锁的粒度越大，数据库所能封锁的数据单元就越少，并发度就越小，系统开销也越小；封锁的粒度越小，并发度较高，但系统开销也就越大。课件用两个例子把这一对矛盾讲透：若封锁粒度是数据页，T1 需要修改元组 L1，就必须对包含 L1 的整个数据页 A 加锁，T2 要修改同页的元组 L2 只能等待；若粒度是元组，T1、T2 可同时对 L1、L2 加锁，不必互相等待，并行度提高。反过来，事务 T 要读取整张表，若粒度是元组，T 必须对表中每一个元组加锁，开销极大。

选择封锁粒度的原则是同时考虑封锁开销和并发度两个因素，适当选择，课件给出三条对应关系：需要处理多个关系的大量元组的用户事务，以数据库为封锁单位；需要处理大量元组的用户事务，以关系为封锁单元；只处理少量元组的用户事务，以元组为封锁单位。

多粒度封锁（Multiple Granularity Locking）是在一个系统中同时支持多种封锁粒度供不同的事务选择。它用多粒度树以树形结构表示多级封锁粒度：根结点是整个数据库，表示最大的数据粒度；叶结点表示最小的数据粒度。课件的例子是三级粒度树：根结点为数据库，数据库的子结点为关系，关系的子结点为元组。

多粒度封锁协议有三条要点：允许多粒度树中的每个结点被独立地加锁；对一个结点加锁意味着这个结点的所有后裔结点也被加以同样类型的锁；在多粒度封锁中一个数据对象可能以两种方式封锁——显式封锁与隐式封锁。显式封锁是直接加到数据对象上的封锁；隐式封锁是该数据对象没有独立加锁，是由于其上级结点加锁而使该数据对象加上了锁。二者效果是一样的。

正因为隐式封锁同样有效，系统检查封锁冲突时不能只看目标对象本身。对某个数据对象加锁，系统要检查三处：①该数据对象上有无显式封锁与之冲突；②所有上级结点——检查本事务的显式封锁是否与该数据对象上的隐式封锁（由上级结点已加的封锁造成）冲突；③所有下级结点——看上面的显式封锁是否与本事务的隐式封锁（将加到下级结点的封锁）冲突。

例：事务 T 要对关系 R1 加 X 锁，系统必须搜索其上级结点（数据库、关系 R1），还要搜索 R1 的下级结点，即 R1 中的每一个元组；如果其中某一个数据对象已经加了不相容锁，T 就必须等待。在三级粒度树下，一个关系可能包含成千上万个元组，逐元组检查的代价正是 11.7.2 要引入意向锁的理由。

粒度选择的"一对矛盾 + 三条对应"与多粒度树的三条规则，是简答与填空的常客。

  • 粒度越大：并发度越小、开销越小；粒度越小：并发度越大、开销越大。

易错

例题

补充例题：三级粒度树中，T1 对关系 R1 加了 X 锁。问：(1) T2 对 R1 中元组 t1 请求 S 锁能否批准？(2) T2 对另一关系 R2 请求 X 锁能否批准？(3) 若 T1 只对 t1 加了 X 锁，T2 对 R1 请求 S 锁时要检查什么？

(1) 不能。对 R1 加 X 锁意味着 R1 的所有后裔（含 t1）都被隐式地加了 X 锁，t1 上的 S 锁请求与隐式 X 锁冲突，T2 只能等待。(2) 能。R2 不是 R1 的后裔，也不在 R1 的上级路径上，只要数据库结点上没有不相容的锁即可批准；T1 锁 R1 时若按多粒度规则需在数据库上留 IX 锁，而 R2 的 X 锁请求对数据库上的 IX 锁相容（表 7 中 IX–IX 为 Y）。(3) 要检查上级结点（R1 上的显式封锁与 t1 的隐式 X 锁是否冲突）与下级结点（R1 的 S 锁会隐式锁住全部元组，需确认各元组上没有不相容的 X 锁）。
关键结论：检查范围 = 自身 + 全部祖先 + 全部后代。

11.7.2意向锁

引进意向锁（Intention Lock）的目的是提高对某个数据对象加锁时系统的检查效率。上节的检查要遍历全部后裔，在元组数很大时不可接受。课件给了一个具体场景：Student 表有 100 万条数据，程序员 A 发现有些学生年龄是负数，打算把负数改成正数，并且修改时别人不可读取，于是他对那两行数据加了 X 锁；程序员 B 发现有几个姓名写错，打算给整张表加 S 锁（别人可读不可改）。此时数据库要判断"这张表能否加 S 锁"，若没有意向锁，就必须检查 100 万行中有没有 X 锁——如果被加锁的两行恰好在最后，要判断 100 万次才能得出"有一行加了 X 锁，该表不能加 S 锁，请等待"的结论，速度非常慢。

有了意向锁，A 给行加 X 锁的同时对该表加 IX 锁；B 在申请表 S 锁之前，一看到表上有 IX 锁，就马上知道需要等待，不必再去逐行判断。规则是：如果对一个结点加意向锁，则说明该结点的下层结点正在被加锁；对任一结点加基本锁，必须先对它的上层结点加意向锁。例如对任一元组加锁时，必须先对它所在的数据库和关系加意向锁。

常用的意向锁有三种。IS 锁（意向共享锁，Intent Shared Lock）：对一个数据对象加 IS 锁，表示它的后裔结点拟（意向）加 S 锁；例：事务 T1 要对 R1 中某个元组加 S 锁，则要首先对关系 R1 和数据库加 IS 锁。IX 锁（意向排它锁，Intent Exclusive Lock）：对一个数据对象加 IX 锁，表示它的后裔结点拟加 X 锁；例：T1 要对 R1 中某个元组加 X 锁，则要首先对关系 R1 和数据库加 IX 锁。SIX 锁（共享意向排它锁，Shared and Intention Exclusive Lock）：对一个数据对象加 SIX 锁，表示对它加 S 锁再加 IX 锁，即 SIX = S + IX；例：对某个表加 SIX 锁，表示该事务要读整个表（对该表加 S 锁），同时会更新个别元组（对该表加 IX 锁）。

锁的强度是指它对其它锁的排斥程度。课件给出的强弱次序是 X > SIX > S > IX > IS；一个事务在申请封锁时以强锁代替弱锁是安全的，反之则不然。例如某处本应申请 S 锁而申请 X 锁，只会更严格、不会出错；本应申请 X 锁却申请 S 锁，就允许了别人读取，破坏了隔离性。

具有意向锁的多粒度封锁方法有两条次序规则：申请封锁时应该按自上而下的次序进行，释放封锁时则应该按自下而上的次序进行。例如事务 T1 要对关系 R1 加 S 锁：要首先对数据库加 IS 锁；然后检查数据库和 R1 是否已加了不相容的锁（X 或 IX）；此时不再需要搜索和检查 R1 中的元组是否加了不相容的锁（X 锁）——因为若某元组上有 X 锁，其上级关系上必然留有 IX 锁，在检查 R1 时就已发现。这样做提高了系统的并发度、减少了加锁和解锁的开销，在实际数据库管理系统产品中得到广泛应用。

考点 · 必背

意向锁的定义、"谁加在哪一级"、相容矩阵与加锁次序，是本章第二必考简答，常与多粒度树一起出。

  • 目的：提高加锁时检查冲突的效率，避免遍历全部后裔。
  • IS：后裔拟加 S 锁；IX：后裔拟加 X 锁；SIX = S + IX（读整个表 + 改个别元组）。
  • 规则：加意向锁说明下层正在被加锁；加基本锁前必须先给所有上层结点加意向锁。
  • 次序：加锁自上而下，解锁自下而上；对元组加 X 锁 → 关系加 IX、数据库加 IX。
  • 强度：X > SIX > S > IX > IS；以强代弱安全，以弱代强不安全。

易错

① 对元组加 X 锁却给关系加 IS 锁——错在"意向类型要与实际锁类型匹配"：加 X 锁须用 IX，加 S 锁才用 IS。② 以为意向锁是加在下级结点上的——它恰恰加在上级结点，用来"预告"下级将要加什么锁。③ 以为 SIX 等于"S 锁和 IX 锁二选一"——它是两者同时持有，语义是"整表读 + 个别行写"。④ 认为 S 与 IX 相容：表 7 中为 N，因为 IX 意味着下级将要写，表级 S 会挡住它。⑤ 把加锁次序写成自下而上：加锁自上而下、解锁自下而上，方向写反即扣分。

例题

补充例题：三级粒度树（数据库 D → 关系 R2 → 元组 t）。事务 T 要修改 R2 中的元组 t，写出它应加的完整封锁序列（自上而下），并说明系统在每一步检查什么；若此时另一事务已对 D 加了 S 锁，T 能否继续？

封锁序列：IXlock D → IXlock R2 → Xlock t。第一步对数据库加 IX 锁，声明后裔拟加 X 锁；第二步对关系 R2 加 IX 锁，声明其下有元组要写；第三步才对元组 t 加 X 锁。系统检查的内容是：加 IXlock D 时看 D 上有无 X、S、SIX 等不相容锁；加 IXlock R2 时看 R2 上的显式锁以及由 D 上锁造成的隐式锁；加 Xlock t 时看 t 上的显式锁与上级的隐式锁。
若另一事务已对 D 加 S 锁：查表 7，S 与 IX 不相容（N），T 的 IXlock D 请求必须等待；这正说明"表级 S 锁会阻塞任何要改行的意图"，也是 SIX 存在的理由（既要读全表又要改个别行时，用 SIX 而不是 S）。

口诀：IS 想读、IX 想写、SIX 表读行写；上加下放、强弱有序——前半句记三种意向锁语义，后半句记加锁自上而下、解锁自下而上，强度 X > SIX > S > IX > IS。

11.9小结

全章是一条因果链：并发执行破坏隔离性 → 用封锁控制 → 封锁要约定规则（三级封锁协议）→ 规则带来活锁与死锁 → 调度是否正确用可串行性衡量 → 用两段锁协议保证可串行 → 粒度与意向锁解决效率。复习时按这条链回忆，比按小节背更不容易漏。

课件 11.9 小结把结论压成四句：数据库的并发控制以事务为单位；通常使用封锁机制，包括基本封锁与多粒度封锁；封锁会带来活锁和死锁；并发事务调度的正确性用可串行性衡量，而并发操作的正确性通常由两段锁协议保证，两段锁协议是可串行化调度的充分条件而非必要条件；此外还有冲突可串行性这一更严格、可机械判定的条件。

11.8 节"其它并发控制机制"在课件中标星，只需记住名字与一句话思想：时间戳（Timestamp）方法给每个事务分配时间戳，按时间戳次序等价地保证可串行化，冲突时撤销时间戳较晚的事务；乐观控制法先让事务自由执行，提交前再做冲突校验，冲突则回滚；多版本并发控制（MVCC）保留数据的多个版本，使读操作不必等待写操作。三者与封锁并列，都是并发控制的主要技术。

考点 · 必背

把下面五条串成一段话，就是本章简答题的标准答案骨架。

  • 并发控制以事务为单位，用封锁保证隔离性；三级封锁协议分别防丢失修改、脏读、不可重复读。
  • 活锁用先来先服务解决；死锁用预防（一次封锁、顺序封锁）或诊断（超时、等待图）解决，解除时撤销代价最小的事务。
  • 可串行性是正确调度的准则；冲突可串行化是其充分条件，用优先图无回路判定。
  • 2PL 是可串行化的充分不必要条件，不能避免死锁；一次封锁法遵守 2PL。
  • 粒度越大并发度越低、开销越小；意向锁 IS/IX/SIX 用于提高多粒度封锁的检查效率。
口诀：锁—协议—活死锁—可串行—两段锁—粒度意向锁——六个词就是本章六节，答题时按词展开，每词一句结论即可成段。

本节小结

  • 全章主线：不一致性 → 封锁 → 封锁协议 → 活锁死锁 → 可串行性 → 两段锁 → 粒度与意向锁。

  • 效率上靠封锁粒度与意向锁：粒度换并发度，意向锁换检查开销。
